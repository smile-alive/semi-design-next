## 使用场景

Popover 气泡卡片是由用户自主打开的临时性浮层卡片，能够承载一些额外内容和交互行为而不影响原页面。

和 Tooltip 的区别是，它可以承载更复杂的内容，而不仅仅是提示文本。

### 注意事项

<Framework only="react">

Popover 需要将 DOM 事件监听器应用到 children 中，如果子元素是自定义的组件，你需要确保它能将属性传递至底层的 DOM 元素

同时为了计算弹出层的定位，需要获取到 children 的真实 DOM 元素，因此 Popover 支持如下类型的 children

1. Class Component，不强制绑定ref，但需要确保 props 可被透传至真实的 DOM 节点上
2. 函数式组件，将 props 与 ref（React 19 中 ref 是普通 prop）透传到 children 内真实的 DOM 节点上
3. 真实 DOM 节点, 如 span，div，p...

</Framework>

<Framework only="vue">

Popover 需要将触发属性和事件监听器应用到默认插槽的触发元素上，并以触发元素的真实 DOM 元素计算弹出层的定位，因此默认插槽支持如下类型：

1. 单个真实 DOM 元素，如 span，div，p...
2. 单个组件，需要让未声明的属性落到它的根 DOM 元素上（默认的 attrs 透传即可）；根为多个节点的组件以它的第一个元素为锚点
3. 文本或多个节点，Popover 会用一个 span 包裹它们作为触发元素

</Framework>

<Framework only="solid">

Popover 需要将触发属性和事件监听器应用到触发元素上，并以触发元素的真实 DOM 元素计算弹出层的定位，因此 `children` 支持如下类型：

1. 函数：入参 `trigger` 即 `getTriggerProps`，把 `trigger()` 展开到接收焦点的元素上，该元素可以是真实 DOM 元素（如 span、div、p...），也可以是会把属性透传到根 DOM 元素的组件（如 `<Button {...trigger()} />`）
2. 其他内容（文本、组件、多个节点）：Popover 会用一个 span 包裹它们作为触发元素

</Framework>

### condition 条件触发

<Framework only="react">

当 `condition={false}` 时，Popover 不响应 hover/click/focus 等触发行为（`trigger='custom'` 不受影响）；condition 由 true 变为 false 时，已显示的弹出层立即关闭；`visible` 受控时只调用 `onVisibleChange(false)`，使用方回写 `visible` 后才关闭。

</Framework>

<Framework only="vue">

当 `:condition="false"` 时，Popover 不响应 hover/click/focus 等触发行为（`trigger="custom"` 时仍按 `visible` 显示）；condition 由 true 变为 false 时，已显示的弹出层立即关闭；`visible` 受控时只发出 `update:visible` 与 `visibleChange(false)`，使用方回写 `visible` 后才关闭。

</Framework>

<Framework only="solid">

当 `condition={false}` 时，Popover 不响应 hover/click/focus 等触发行为（`trigger="custom"` 不受影响）；condition 由 true 变为 false 时，已显示的弹出层立即关闭；`visible` 受控时只调用 `onVisibleChange(false)`，使用方回写 `visible` 后才关闭。

## Accessibility

### ARIA

- 关于 role
    - 当 Popover 的 trigger 为 click、contextMenu、custom 时，Popover 的 content 具有 `dialog` role
    - 当 trigger 为 hover、focus 时，Popover 的 content 具有 `tooltip` role
    - `role` 属性可覆盖默认值。`dialog` 需要名称：传入 `aria-label`，或用 `aria-labelledby` 指向 content 中的标题；未命名的 dialog 在开发环境会输出警告
- Popover 的 content
    - content 的 wrapper 会被自动添加 `id` 属性
- Popover 的 children（`tooltip` 只会被添加 `aria-describedby`；`presentation` 等其他 role 不添加任何属性）
    - 会被自动添加 [aria-expanded](https://www.w3.org/TR/wai-aria-1.1/#aria-expanded) 属性，当 Popover 可见时，属性值为 `true`，不可见时为 `false`
    - 会被自动添加 [aria-haspopup](https://www.w3.org/TR/wai-aria-1.1/#aria-haspopup) 属性，为 `dialog`
    - 会被自动添加 [aria-controls](https://www.w3.org/TR/wai-aria-1.1/#aria-controls) 属性，为 content 的 wrapper 的 id

### 键盘和焦点

- Popover 触发方式设置为 hover 时：鼠标悬浮或聚焦时打开 Popover
- Popover 触发方式设置为 click 时：点击触发器或聚焦时并使用 Enter 键打开 Popover
- Popover 激活后，按下方向键 ⬇️ 将焦点移动到 Popover 上，此时焦点默认处于 Popover 中第一个可交互元素上，用户也可自定义焦点位置（若 Popover 内无可交互元素则表现为无响应）
- 焦点处于 Popover 内时使用 Tab 键，焦点会在 Popover 内循环，使用 Shift + Tab 会反方向移动焦点
- 键盘用户能够通过按 Esc 关闭 Popover，关闭后焦点返回到触发器上（仅当 trigger 为 click 时）

## FAQ

- **为什么 Popover 浮层卡片的位置和浮层的触发器的相对位置不符合预期?**  
  Popover 底层依赖了 Tooltip，Tooltip 为了计算定位，需要获取到 children 的真实 DOM 元素，因此 Popover 类型目前支持如下类型的 children：

      <Framework only="react">
    1. Class Component，不强制绑定ref，但需要确保 props 可被透传至真实的 DOM 节点上
    2. 函数式组件，将 props 与 ref（React 19 中 ref 是普通 prop）透传到 children 内真实的 DOM 节点上
    3. 真实 DOM 节点, 如 span，div，p...

    若通过 ref 或 findDOMNode 获取到的真实 DOM 节点宽高并非是你的 children 元素的全部，则位置可能有出入。例如设置了 prefix、suffix 的 Input，Popover位置仍是相对于不包含前缀部分的 input 框进行定位，此时只要在 Input 外层再套一个 div 就能解决问题。

      </Framework>

      <Framework only="vue">
    1. 单个真实 DOM 元素，如 span，div，p...
    2. 单个组件，未声明的属性需要落到它的根 DOM 元素上；根为多个节点的组件以它的第一个元素为锚点
    3. 文本或多个节点，由 Popover 用一个 span 包裹

    若触发元素的真实 DOM 节点宽高并非是你的触发内容的全部，则位置可能有出入。例如设置了 prefix、suffix 的 Input，Popover位置仍是相对于不包含前缀部分的 input 框进行定位，此时只要在 Input 外层再套一个 div 就能解决问题。

      </Framework>

      <Framework only="solid">
    1. 函数：把 `trigger()` 展开到真实 DOM 元素，或展开到会把属性透传到根 DOM 元素的组件上
    2. 其他内容（文本、组件、多个节点），由 Popover 用一个 span 包裹

    若触发元素的真实 DOM 节点宽高并非是你的触发内容的全部，则位置可能有出入。例如设置了 prefix、suffix 的 Input，Popover位置仍是相对于不包含前缀部分的 input 框进行定位，此时只要在 Input 外层再套一个 div 就能解决问题。

      </Framework>

- **为什么 Popover 浮层卡片在靠近屏幕边界宽度不够时，丢失宽度意外换行?**  
  在 chromium 104 后 对于屏幕边界文本宽度不够时的换行渲染策略发生变化，详细原因可查看 [issue #1022](https://github.com/DouyinFE/semi-design/issues/1022)，semi侧已经在v2.17.0版本修复了这个问题。
