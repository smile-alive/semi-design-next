# 整理代码库

启动一次彻底的重构，并把它做到底，当作一个目标来完成。

为什么要这样做：

- **更好的输出**：在结构良好的代码库中，代理编写的代码质量更高。
- **更低成本、更快的变更**：代理花在搜索上的 token 更少，可以把更多精力放在问题本身上。
- **更少静默破坏**：代理在不知不觉中造成破坏的概率更低。
- **更快调试**：代理能更快找到根因。

## 1 先询问

除了整理代码库之外，还有两件可选的事：

| 可选项       | 作用                                                                            |
| ------------ | ------------------------------------------------------------------------------- |
| **Comments** | 删除那些只是在重复代码的注释。                                                  |
| **Tests**    | 删除那些不能真正抓住真实 bug 的测试，并修复那些在没有对应错误时也会失败的测试。 |

把这两项按上表的原话列给用户，询问要执行哪些，然后只做用户选中的。

## 2 列出每一个问题

列完问题之前不要改代码。

逐个检查整个代码库，只问一个问题：这些部分是否应该一起变化？把代码答错的每一处都按 [决策日志示例](#决策日志示例) 的格式写下来。

### 隐藏链接

必须一起变化，但代码没有显示出它们之间的关系。

- **逻辑或值的复制**：改其中一个，其他地方也必须同步改动，但没有任何地方说明它们相关。
- **读取另一个模块设置的全局变量或文件**：改了这个模块，另一个模块就会失效，但代码没有表明这种依赖（自包含代码）。
- **按层拆分的功能，或者相关代码分散在不同文件夹**：一次改动要涉及所有相关位置，但代码结构掩盖了它们的联系（领域驱动代码、就近放置）。
- **必须按固定调用顺序或约定使用的代码**：调用方必须知道这个顺序或约定，改了以后调用方就会出错，但代码没有给出警告（显式依赖胜过隐式依赖）。

### 无谓的链接

本来不该绑在一起，却因为不同原因被强行耦合。

- **调用方依赖内部实现**：内部实现出于自身原因变化，调用方也被迫跟着变（封装不足）。
- **稳定的代码依赖更容易变化的东西**：稳定代码必须随着易变代码一起改（依赖方向错误）。
- **通用函数带着只有某个工作流才理解的参数**：那个工作流一变，这个函数就得跟着改（调用方词汇污染）。
- **浅层模块**：接口每次都随内部实现一起变，调用方也要跟着改（缺少深层模块）。

### 剩余冗余

本身没有任何理由需要变化。

- **包装器**：只会在被包装的对象变化时跟着变（传递式包装）。
- **从未变化的扩展点和配置**：永远不会变，不值得为它们设计通用机制（过度前瞻的通用性）。
- **死代码**：没人使用，也就永远不需要变化。

### 特殊情况

还要记录每一个特殊情况：为处理某种特定情况而存在、不遵循系统设计逻辑的代码。每个特殊情况都说明设计漏掉了一个需求，要把它们当作真正的约束，指导后续重构。

- 只针对某个值的 `if`
- 只给某个调用方使用的参数
- 被吞掉的异常
- 重试或 sleep
- 被禁用的测试

## 3 从第一性原理重新设计

假设系统从一开始就知道今天的需求，重新构思修复方案。寻找多个问题背后共同的根本修复，它往往看起来和问题本身毫无关系。不要一条条修特殊情况，要从结构上修复。

对每个修复都问同一个问题，即使另一种方案在代码里看起来更好：应该一起变化的部分是否最终放在了一起，不该绑在一起的部分是否没有被强行联系，所有东西是否都依赖于变化更少的东西。

把每个修复写在它所解决的问题上方，格式见 [决策日志示例](#决策日志示例)。

## 4 修复清单上的所有问题

移除重构后不再需要的特殊情况，保留系统仍然需要的。不要额外寻找新的 bug；结构性修复顺带修掉一些问题没关系。

用户选了 **Comments** 时：

- **重复实现的注释**，例如 `// sort first so the binary search works`：只会跟着实现一起变化，没有独立的变化理由。删除，即使它们看起来有帮助。
- **描述代码外部事实的注释**，例如 `// the proxy drops websockets, so we poll`：会随外部事实改变，而代码本身无法表达这一点。保留。
- **解释临时解决方案的注释**，例如 `// wait 100ms because the cache isn't ready yet`：只会跟着根因变化。重构消除了这个问题时，注释一并删除。

用户选了 **Tests** 时，放到最后做，因为测试是回归安全网。测试只有在回归发生时才失败，才值得保留：

- **重复实现的测试**：只会跟着实现一起变化，只是拿同一种解释和自己比较。删除。
- **绑定到内部实现的测试**：代码变了但行为没变时也会失败，是为错误的原因而变化。改写为依赖行为，行为变化得更少。
- **不会失败的测试**：无论代码如何都会通过，没有检查任何真实内容。删除。

## 5 检查并重复，直到完成

让子代理搜寻特殊情况、隐藏链接、无谓的链接和冗余。直到没有值得修的东西才停下。

完成的标准：

- 系统中留下的特殊情况尽可能少。它们的数量是衡量离完成还有多远的最好指标。
- 一次典型改动通常只落在一个地方。
- 每个 import 都有理由，没有任何东西依赖比自己更易变的东西。
- 子代理再也找不到值得修的问题。
- 除了重构修掉的 bug，行为与开始时相同。最后用测试验证。

## 提示

- **从骨架开始**：先用脚本去掉函数体，让整个代码库能放进上下文。
- **用子代理汇总**：让它们总结代码库的各个部分，你在全局范围内推理。
- **经常检查依赖图**：用脚本生成「谁 import 谁」的图，在过程中反复检查。
- **先看杠杆最大的位置**：从那里着手。
- **保留决策日志**：压缩信息比丢失上下文好。
- **用 Git 作为证据**：看哪些部分变化频繁，哪些变更总是一起发生。

## 决策日志示例

问题按根本修复分组，每个修复写在它解决的问题上方：

```md
修复：建立统一的动作注册表。每个动作只在一处声明 id、名称、快捷键、`isEnabled`、`run`，可撤销的再加 `undo`；
工具栏、菜单、快捷键和命令面板都从注册表渲染，派发器统一调用 `track()`。

- `ui/Toolbar.tsx:40` 和 `ui/Menu.tsx:22` 调用相同的动作，但每个地方都有自己的一套禁用状态检查。
- `shortcuts/keymap.ts:18` 有一个 switch，里面针对每个动作都有一个 case，而且它和菜单中的列表是分开的。
- `ui/CommandPalette.tsx:55` 自己维护一份动作列表，而且缺少较新的动作。
- `history/undo.ts:30` 对每种可撤销动作都写了一段特殊处理。
- 每个动作处理器都必须手动调用 `track()`，而且有些地方漏了。
- `ui/Toolbar.test.tsx` 和 `ui/Menu.test.tsx` 分别测试了相同的动作。

修复：对话框关闭时由对话框自己把焦点还给打开它的元素，嵌套对话框按栈逐层归还。

- `ui/LogoutDialog.tsx:30` 在关闭后等待 100ms，并希望消息输入框能在那时获得焦点。
- `ui/SettingsDialog.tsx:61` 设置了一个全局 `skipRefocus` 标志，用来阻止它打开的退出登录对话框把焦点发送回消息输入框。

修复：结账和退款依赖 `PaymentProvider` 接口，Stripe 和 PayPal 各自实现，按 `order.provider` 选择实现。

- `checkout/submit.ts:9` 直接依赖 `payments/stripe.ts`。
- `refunds/refund.ts:22` 对每个 Stripe 调用都包了一层 `if (order.provider === "paypal")`。
```
